1. STACK TECHNIQUE
------------------------------------------------------------------------------

BACKEND (Jakarta EE 11 / Java 21)
  - JUnit 5.13.2        — framework de test
  - Mockito 5.14.2      — mocks des repositories et collaborateurs
  - AssertJ 3.27.3      — assertions lisibles et chaînables
  - jersey-common 3.1.10 (scope test uniquement) — fournit un
    RuntimeDelegate JAX-RS pour pouvoir instancier les exceptions
    (BadRequestException, NotFoundException, ForbiddenException)
    en dehors d'un container Payara.
  - maven-surefire-plugin 3.5.3 — exécution depuis Maven

FRONTEND (React 19 / Vite)
  - Vitest 4               — runner de test (compatible Jest API)
  - jsdom                  — environnement DOM en mémoire
  - @testing-library/react — rendu et requête des composants
  - @testing-library/jest-dom — matchers DOM (toBeInTheDocument…)
  - @testing-library/user-event — simulation des interactions clavier/souris
  - @vitest/coverage-v8    — rapport de couverture

------------------------------------------------------------------------------
3. LANCER LES TESTS
------------------------------------------------------------------------------

Backend (depuis JOALABFT_Backend/) :

    ./mvnw test                                  # toute la suite
    ./mvnw test -Dtest=PermissionServiceTest     # une seule classe
    ./mvnw test -Dtest=FicheServiceTest#updateFiche_suppressionLigne_appelleFlushEntreDeleteEtInsert
                                                 # une seule méthode

Frontend (depuis joalabft_frontend/) :

    npm test                                     # exécution unique
    npm run test:watch                           # mode watch
    npm run test:coverage                        # rapport de couverture v8

Les deux suites tournent en quelques secondes et n'ouvrent aucun port :
les tests sont totalement hors ligne, sans base de données ni HTTP réel.

4. PÉRIMÈTRE ET CHOIX DE COUVERTURE
------------------------------------------------------------------------------

La cible définie au démarrage est "tests minimaux pour passer un quality gate" :
pour chaque méthode publique sensible, on couvre au moins le happy path
et la première erreur attendue (403, 404, validation, etc.).

DANS LE PÉRIMÈTRE
  - Services métier backend (PermissionService, FicheService,
    UtilisateurService, ClientService, AuthService, JournalService,
    SessionStore, AdresseService).
  - Utilitaires backend (WorkDay, PasswordHasher).
  - Utilitaires frontend (permissions, formatters, libelle, champsClient,
    print).
  - Composants frontend critiques pour la sécurité ou pour l'UX
    (ConfirmDialog, ClientMatchDialog, Login).

HORS PÉRIMÈTRE (volontairement non couverts pour cette première passe)
  - Controllers JAX-RS (testés en intégration future si besoin via
    Arquillian ou un Payara embarqué).
  - Repositories (couverts indirectement par les services mockés).
  - Pages frontend complexes : AjoutFiche, EditFiche, DetailFiche,
    DetailClient, ListeClients, ListeUtilisateurs, Journal, Accueil,
    ImporterClients. À étendre dans une deuxième passe.
  - Tests end-to-end (Playwright/Cypress) — non installés.

5. CONVENTIONS DE NOMMAGE ET DE STRUCTURE
------------------------------------------------------------------------------

NOM DES TESTS BACKEND

Format : sujet_situation_resultatAttendu

Exemples :
  - login_motDePasseFaux_retourneNull
  - updateFiche_suppressionLigne_appelleFlushEntreDeleteEtInsert
  - mcd_nePeutPasSAutoArchiver

L'avantage : à la lecture des échecs Surefire, on comprend immédiatement
quel scénario casse, sans devoir ouvrir le fichier de test.

STRUCTURE D'UN TEST (Arrange / Act / Assert)

    @Test
    void description_du_scenario() {
        // Arrange — prépare les données et les mocks
        Utilisateur mcd = TestEntities.mcd(1);
        when(repository.findById(7L)).thenReturn(Optional.of(...));

        // Act — appelle la méthode testée
        service.metier(7L, mcd);

        // Assert — vérifie l'état observable et les interactions
        verify(repository).update(...);
        assertThat(...).isEqualTo(...);
    }

NOM DES TESTS FRONTEND

Format Vitest : describe('Sujet', () => { it('comportement attendu') })

Exemples :
  - it('CAISSIER peut modifier la fiche du jour et de la veille')
  - it('bouton Fusionner désactivé si pas de différence')

6. OUTILS D'ISOLATION
------------------------------------------------------------------------------

BACKEND — MOCKITO SUR LES REPOSITORIES

Choix structurant : pour chaque service, les repositories sont remplacés
par des mocks Mockito. Aucun test backend n'ouvre de base H2 ni de
PersistenceContext réel. Avantages :
  - exécution en quelques millisecondes par test ;
  - on isole la logique métier des détails JPA ;
  - les scénarios d'erreur (NotFound, BadRequest) sont triviaux à provoquer.

Inconvénient assumé : les bugs purement liés à la persistance (orphan
removal, casts JPA, requêtes JPQL) ne sont pas détectés ici. Le seul test
qui s'en approche est :

    FicheServiceTest.updateFiche_suppressionLigne_appelleFlushEntreDeleteEtInsert

qui vérifie l'ordonnancement flush() → update() à l'aide d'un InOrder,
pour empêcher la régression du bug "ligne supprimée dupliquée" observé
en déploiement Docker.

FABRIQUE D'ENTITÉS

TestEntities.java injecte par réflection les identifiants normalement
générés par la base. Les helpers fournis :

    TestEntities.mcd(1)           → Utilisateur MCD avec id=1
    TestEntities.responsable(2)   → Utilisateur RESPONSABLE_CAISSE avec id=2
    TestEntities.caissier(3)      → Utilisateur CAISSIER avec id=3
    TestEntities.client(10, "Dupont", "Marie")
    TestEntities.fiche(7, client, mcd, date)
    TestEntities.ligne(1, fiche)

Tous les tests utilisent ces fabriques plutôt que d'instancier les
entités directement — uniformise les setups et simplifie la lecture.

FRONTEND — MOCK DES MODULES VIA vi.mock()

Pour Login.test.jsx, on mocke api/auth.js, AuthContext.jsx et
react-router-dom. Le composant s'exécute alors complètement isolé du
réseau et de la navigation. Les assertions portent sur les appels à
signIn() et navigate('/accueil').

Pour les tests d'utilitaires, aucun mock : ce sont des fonctions pures.

Pour les composants (ConfirmDialog, ClientMatchDialog), on rend dans
jsdom via @testing-library/react et on simule les clics avec
userEvent — proche du comportement réel d'un utilisateur.

7. CAS PARTICULIER : REPRODUIRE UN BUG PAR UN TEST
------------------------------------------------------------------------------

Le bug "suppression de ligne dupliquée" en Docker (mai 2026) a été reproduit
et figé par le test :

    FicheServiceTest.updateFiche_suppressionLigne_appelleFlushEntreDeleteEtInsert

Le test :
  1. Place une fiche avec 2 lignes (id=1 et id=2) dans le mock du repository.
  2. Construit une requête de mise à jour qui conserve la ligne 1, supprime
     la ligne 2 et ajoute une troisième ligne.
  3. Vérifie via InOrder que flush() est appelé sur le repository AVANT
     update(fiche). Si le code régressait et retirait le flush(),
     l'assertion échouerait.

Cette approche — "écrire un test qui aurait attrapé le bug" — est la
méthode à privilégier pour chaque correctif important.

8. MAINTENANCE
------------------------------------------------------------------------------

QUAND AJOUTER UN TEST
  - Tout nouveau endpoint REST → au moins un test sur le service appelé.
  - Toute modification d'une matrice de droits → un test par rôle impacté
    dans PermissionServiceTest ET dans permissions.test.js (les deux
    miroirisent les mêmes règles).
  - Tout bug corrigé → un test qui aurait attrapé le bug.

CI / INTÉGRATION
  Les commandes ./mvnw test (backend) et npm test (frontend) sont prêtes
  à être branchées dans un workflow GitHub Actions ou GitLab CI. Aucune
  variable d'environnement, aucun service externe requis.

MISE À JOUR DU TABLEAU
  Le fichier tableau_tests.csv n'est PAS généré automatiquement. À chaque
  ajout/suppression de test, mettre à jour la ligne correspondante et
  l'état (Passé/Échoué) en relançant la suite.

9. ACTEURS MÉTIER RÉFÉRENCÉS DANS LE TABLEAU
------------------------------------------------------------------------------

MCD                    Maître Croupier Directeur. Rôle administratif le plus
                       élevé. Peut créer tout type de compte, supprimer
                       fiches/clients, lire le journal d'audit, modifier
                       une fiche quelle que soit son ancienneté.

Responsable Caisse     Rôle intermédiaire. Peut modifier les fiches jusqu'à
                       31 jours dans le passé, modifier l'identité complète
                       d'un client, créer des comptes Caissier, importer
                       des clients en masse, lire l'historique d'une fiche.

Caissier               Rôle quotidien. Peut créer des fiches, modifier
                       celles du jour et de la veille, mettre à jour
                       l'adresse et la pièce d'identité d'un client.

Anonyme                Visiteur non authentifié, ou utilisateur dont la
                       session a expiré. Couvre les tests de login KO et
                       de token invalide.

Utilisateur authentifié
                       Acteur générique quand le rôle exact n'a pas
                       d'importance dans le scénario testé (ex : log
                       d'audit, autocomplétions).

Utilisateur archivé    Compte précédemment archivé par un MCD. Ne peut
                       plus se connecter mais reste référencé dans les
                       fiches historiques.

Tous rôles             Test paramétré qui balaie {MCD, Responsable Caisse,
                       Caissier} pour vérifier qu'une règle s'applique
                       uniformément.

Système                Couche utilitaire pure (calcul de date, formatage,
                       hash). Sans utilisateur final dans la boucle.
